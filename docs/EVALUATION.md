## 1. Setup and honest caveats

- **Dataset:** 133 files (125 valid + 8 deliberately corrupted), generated with seed 42 by `evaluation/generate_dataset.py`: digital PDFs (3 layouts, incl. 3-invoice PDFs), scanned PDFs, PNG/JPG/TIFF (half clean, half degraded: rotation, blur, noise, down-scaling, JPEG artefacts), CSV, multi-sheet XLSX, legacy XLS, injected arithmetic errors, missing fields, duplicates.
- **The dataset is synthetic.** Layouts are cleaner and more regular than real supplier invoices, so *real-world accuracy will be lower*. Treat these numbers as a regression baseline and an upper bound; re-run against a hand-labelled sample of the company's own documents before go-live.
- **Extractor under test:** `heuristic (rule-based)`. The LLM path is unit-tested with a mocked client but was **not** measured here (no API key in the evaluation environment).
- **Hardware/config:** 1 CPU cores, Linux-6.18.44-fc-v185-x86_64-with-glibc2.39, Python 3.12.3; OCR = Tesseract 5.3.4; 4 worker threads.

## 7. Known limitations

- European number formats (`1.234,56`) are handled in the normaliser but the rule-based line-item parser targets `1,234.56`; the LLM path covers this.
- Rule-based extraction relies on common labels (Invoice No, Bill To, Subtotal ...). Unusual layouts need the LLM path.
- Degraded scans lose line items first (small text); these are flagged through `NO_LINE_ITEMS`/arithmetic checks rather than invented.
- Semantic search uses hashed embeddings by default (lexical overlap + synonym map). Set `EMBEDDING_PROVIDER=sbert` for true semantic matching.
